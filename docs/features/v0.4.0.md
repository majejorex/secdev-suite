# v0.4.0: `security-gate` skill (2026-11-03)

Roadmap phase F2. The new skill `secdev:security-gate` writes a GitHub Actions workflow that blocks pull requests on three things. It can also run the three tools locally once.

| Job | Tool | Fails when |
|---|---|---|
| `secrets` | gitleaks 8.30.1, full git history | any commit contains a secret |
| `dependencies` | osv-scanner 2.7.0, every lockfile | a dependency has a known vulnerability not accepted in `osv-scanner.toml` |
| `sast` | Semgrep CE 1.183.0, `p/default`, `--metrics=off` | there is any finding |

## Design decisions

All of them were checked on 2026-11-03 against each project's release page, docs or source code.

- **Only GitHub-owned actions.** The first version used `google/osv-scanner-action`. This repo's own policy ("allow only GitHub-owned actions" plus "require SHA pinning") blocked it with a `startup_failure`. Now gitleaks and osv-scanner are downloaded as release binaries and checked with `sha256sum -c`. The only action left is `actions/checkout`, pinned to a SHA. The gate works under the strictest policy and adds no third-party action to the supply chain (CICD-SEC-3, CICD-SEC-8).
- **No gitleaks action.** Its README says it needs `GITLEAKS_LICENSE` for organization accounts. The binary doesn't.
- **Semgrep without metrics.** `--config auto` can't be combined with `--metrics=off`. Semgrep's source aborts with "Cannot create auto config when metrics are off". The template therefore uses the registry ruleset `p/default`.
- **Repos without packages.** osv-scanner exits with code 128 ("No package sources found") when the lockfile has no packages. `--allow-no-lockfiles` turns that into a warning in the log.
- **Hardened by default (P1-10).** `pull_request` instead of `pull_request_target`, `contents: read` for every job, `persist-credentials: false`, and the Semgrep image pinned by digest.
- **Nothing leaves the machine without saying so.** The skill says what each tool sends: package names to osv.dev and rule downloads from Semgrep. It writes the workflow only after the user's OK.
- **CVE ranking for local runs.** CISA KEV first: downloading the catalog sends nothing. Then EPSS, which receives the CVE IDs, so the skill asks first.

## Dogfooding

This repo now runs the same workflow (`.github/workflows/security.yml`). `test/structure.test.mjs` keeps it identical to the template in `SKILL.md` and checks that:

- every action is pinned to a SHA;
- the image is pinned by digest;
- top-level permissions are `contents: read`;
- the binaries are checked against their SHA-256;
- the workflow has no `pull_request_target` and no `continue-on-error`.

On its first run in CI, Semgrep found two literal U+202E characters (Unicode bidi, "Trojan Source") in `intel/lib.test.mjs`. They were deliberate test inputs and are now written as the `‮` escape, with the same runtime value. The source no longer hides characters.

Other changes in the repo:

- a `package-lock.json` (no dependencies), so osv-scanner has a source and P0-16 holds;
- `security-checklist` points to the gate from P1-02 and from "Escalate";
- the eval runner accepts a `skill` field per case; new cases `gate-setup` and `es-gate-setup`.

## Not verified

- That gitleaks blocks a PR containing a real secret. The exit code 1 on leaks is documented. Testing it would put a secret in this repo's history.
- Fork PRs. The jobs only need `contents: read`, and fork PRs get a read-only token, so they should work.
